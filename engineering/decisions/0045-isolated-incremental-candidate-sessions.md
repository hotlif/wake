# ADR 0045: Isolated incremental candidate sessions

- Status: accepted
- Date: 2026-09-08

## Context

Docs materializes an immutable generated tree for every refresh. Replacing its session with a cold
session discards compiler work even when a startup Rescan changes no inputs or an edit changes one
page. The accepted filesystem and output must nevertheless survive failed candidates unchanged.

## Decision

1. `BuildSession` may derive a retained candidate against a new generation-owned filesystem. It
   reuses compilation state only when the complete typed `BuildOptions` is equal. Otherwise it
   constructs a cold session. One-shot construction and persistent cache formats are unchanged.
2. A candidate copies input cells, task graph metadata, loader inventories and module/link plans;
   immutable task payloads and pure compiler callbacks may share ownership. Resolver and filesystem
   observation caches belong to the candidate. No candidate changes accepted inputs or output.
3. The task engine snapshot requires exclusive access. Callbacks must refer to immutable compiler
   configuration and engine-relative input handles, never an accepted filesystem or mutable plan.
   Related session builds are serialized by a shared build gate because inherited emission callbacks
   share work counters. Unrelated sessions remain independent and each build still runs parallel tasks.
4. Paths invalidation includes observed source identities and generated added/modified/removed paths.
   Structural changes invalidate resolution/topology. Rescan always discards loader and resolver
   observations and rereads authoritative sources; cached pure compiler work may survive. An empty
   generated diff never authorizes skipping a Rescan or declaring readiness early.
5. The dev server adopts the candidate session only at its existing watcher publication gate.
   Failed candidates are discarded without changing the accepted session. The startup fence, lazy
   mount behavior, diagnostic publication and restart-required controls retain their contracts.

## Invariants

- Changed compile options cannot inherit in-memory compiler tasks.
- Candidate input updates and failures cannot change accepted output or observed generated bytes.
- A no-change Rescan performs zero repeated module code generation; an ordinary leaf edit reuses
  unrelated module compilation. Structural edits must match a cold build.
- Every inherited task uses the same compiler/interner identity as its immutable payloads.
- Summary hits retain their parsed AST evidence for cross-module CSS static evaluation, including
  authoritative rescans; a cached task handle alone is not a populated module AST view.
- A candidate generation starts with fresh observations and no committed output.

## Evidence

- `crates/wake_turbo/src/engine.rs`: exclusive task-graph snapshot.
- `crates/wake_bundler/src/session.rs`: typed candidate construction and related-build gate.
- `crates/wake_dev_server/src/lib.rs`: candidate consumption and startup work-count regression.
- `crates/wake_bundler/tests/performance_invariants.rs`: retained candidate isolation and reuse.
- `crates/wake_app/src/lib.rs`: Docs startup/page-edit reuse and failed-source retry integration.

## Consequences

Candidate creation copies graph metadata and shares immutable AST/output payloads, increasing peak
memory while accepted and candidate coexist. It does not promise route-on-demand compilation or
zero filesystem reads during recovery. Existing `WAKE_TIMING` phase output is retained and extended
with Docs materialization and candidate preparation costs; wall-clock improvement requires workload
measurement rather than a fixed timing threshold in CI.

## Validation

- `cargo test -p wake_turbo --lib`
- `cargo test -p wake_turbo --test fork`
- `cargo test -p wake_bundler --test performance_invariants`
- `cargo test -p wake_dev_server`
- `cargo test -p wake_app --lib`
- `cargo test -p wake_bundler --test one_shot --test minifier_acceptance`
- `cargo clippy -p wake_turbo -p wake_bundler -p wake_dev_server -p wake_app --all-targets -- -D warnings`
- `corepack yarn architecture:test` and `corepack yarn architecture:check`

## Supersedes

None.

## Removal plan

No compatibility bridge. Cold candidate creation remains the required fallback for changed options.

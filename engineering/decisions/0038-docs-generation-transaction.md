# ADR 0038: Docs generation directory transaction

- Status: accepted
- Date: 2026-09-02
- Amended by: [ADR 0041](0041-cross-process-docs-generation-transaction.md)

## Context

`wake_docs::generate_with_mode_in` previously updated generated modules one file at a time, then
read the previous manifest to delete stale files, and finally rewrote the manifest. A malformed
manifest, stale-file deletion failure, or later write failure could therefore expose a directory
containing files from two generations. The generated directory is also a trust boundary: its
manifest must never authorize traversal through links, reparse points, hard links, special files,
or non-portable path identities.

## Decision

`wake_docs` is the sole owner of publishing `.wake/**/docs/generated`. Generation first renders
every output into an in-memory, relative-path `BTreeMap`, including a strict manifest. Publication
then:

1. validates the complete existing tree and manifest without mutation;
2. computes content differences using stable logical paths;
3. returns immediately when the generations are identical;
4. writes and validates a complete random sibling staging directory;
5. renames the target to a unique previous-generation sibling;
6. renames the staging directory to the target; and
7. restores the previous directory if installation fails.

After the staging directory becomes the target, the commit is complete. Failure to remove the
previous-generation sibling is best-effort cleanup and cannot be reported as a failed generation.

Page modules follow the same prepare/finalize boundary in memory. `CompiledPage` retains a
structured `PageModulePlan` plus typed `RouteInfo`; navigation mutates only the route, and the final
module and source map are rendered together after navigation is complete. Generated code is never
searched or patched to synchronize metadata.

## Invariants

- Render and old-tree validation happen before the first target-tree mutation.
- The manifest schema rejects unknown fields; entries are sorted, unique, Normal-only paths and
  exclude the manifest itself.
- The declared file set exactly equals the physical regular-file set outside `manifest.json`.
- Generated trees reject symbolic links, Windows reparse points, special files, files with multiple
  hard links, alternate-data-stream colons, and case-equivalent path collisions.
- Staging and previous-generation names never enter generated bytes, aliases, entry paths, or
  `GeneratedProject::changed_files`.
- Page metadata, the route registry, the returned route list, and source maps are projections of
  one finalized typed route; user ESM cannot be mistaken for a generated metadata marker.
- `changed_files` is the content-difference union of the old and new logical generations, including
  retired paths; a no-op does not replace the target directory.
- The two renames occur between siblings on the same filesystem. If the install rename fails after
  the target was moved, Wake attempts restoration before returning the error.

## Evidence

- `crates/wake_docs/src/lib.rs`: `generate_with_mode_in`, `publish_generation_with_ops`,
  `inspect_generation_tree`, `validate_generation_files`, `PageModulePlan`, and the final
  `CompiledPage::render_module` step.
- Unit tests cover malformed manifests leaving the old tree byte-identical, empty legacy
  placeholders, stale retirement, exact change reporting, hard-link and symlink rejection,
  installation rollback, post-commit cleanup failure, final-navigation metadata consistency,
  adversarial user ESM metadata text, and Unicode/long-metadata source maps.

## Consequences

Every changed generation replaces its directory, so open handles or antivirus software can cause
the rename to fail on Windows. That failure is visible before commit and preserves the accepted
tree when restoration succeeds. The implementation does not claim crash durability: files are
flushed before installation, but directories are not fsynced. A process crash after the first
rename may leave the unique previous-generation sibling for later maintenance.

Strict validation intentionally refuses generated trees with untracked files or malformed legacy
manifests instead of guessing ownership. A completely empty pre-created target remains accepted as
a migration-compatible placeholder.

## Validation

- `cargo fmt --check`
- `cargo check -p wake_docs`
- `cargo test -p wake_docs --lib`
- `git diff --check`
- `corepack yarn architecture:check`

Unix CI exercises real symbolic links. Windows symlink coverage is conditional on the process
having link-creation privilege; hard-link and reparse-point rejection remain implemented on that
platform.

## Supersedes

None.

## Removal plan

The per-file write-then-stale-delete path in `generate_with_mode_in` is removed with this decision.
`atomic_write_if_changed` remains the owner of unrelated standalone site-shell and copied-output
writes and is not a compatibility bridge for generated module publication. Unique previous-tree
cleanup is best effort; future startup maintenance may reclaim abandoned siblings only after it can
prove they are not live.

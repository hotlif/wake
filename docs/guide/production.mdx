# 生产构建

生产构建不是把开发服务器目录直接复制出去，而是重新按 production 口径解析、优化和写入静态产物。

## 应用构建命令

使用配置入口：

```bash
wake build --outdir dist
```

显式指定入口：

```bash
wake build src/main.tsx --outdir dist
```

入口选择顺序：

1. 命令行位置参数 `ENTRY`；
2. `[html].entry`；
3. 默认 `src/entry.tsx`。

`--outdir` 默认是 `dist`。Wake 会在构建前清理它，避免旧 hash 文件留在发布目录。

## 文档构建命令

```bash
wake docs build . --outdir docs-dist
```

`.` 是项目根。文档输出目录默认 `docs-dist`，相对路径以项目根解析。

## 依赖扁平化

Wake 在扫描模块图时，以 npm 包的 `name@version` 和包内相对路径作为依赖身份，而不是直接使用磁盘上的安装路径。例如，下列两个文件会进入同一个模块实例：

```text
node_modules/a/node_modules/shared/index.js  → shared@1.2.0/index.js
node_modules/b/node_modules/shared/index.js  → shared@1.2.0/index.js
```

因此，同名、同版本、同子路径的依赖只会打包一次；`shared@1.2.0` 和 `shared@2.0.0` 则会保留为两个独立实例。这一规则同样适用于 npm、pnpm 以及 Yarn PnP 的物理安装布局。

<Callout title="有上下文的包不会被错误合并" tone="info">
带 `peerDependencies` 的包、Yarn PnP 虚拟包以及本地 workspace 包会保留安装上下文。它们即使名称和版本相同，也可能绑定不同的宿主依赖或本地源码，因此不会仅凭 `name@version` 强行合并。
</Callout>

扁平化只统一模块身份，不会把多个 CommonJS 模块拼成一个共享闭包。CommonJS 的初始化顺序、循环依赖和 `module.exports` 生命周期仍由独立模块工厂管理。

## 默认生产优化

应用和文档生产构建会使用以下能力：

- JavaScript 压缩；
- 局部标识符 mangle；
- Dead Module Elimination；
- Tree Shaking；
- 动态 `import()` 代码分割；
- CSS 抽取和压缩；
- 小于 4KB 的资源内联；
- 大资源独立输出并添加内容 hash；
- chunk、CSS 和资源文件名 hash；
- `manifest.json`；
- HTML 外壳。

如果设置环境变量 `WAKE_NO_MANGLE`，文档构建会保留标识符压缩关闭，适合调查第三方包兼容问题，但最终体积可能更大。

## 认识输出文件

```text
dist/
├─ index.html
├─ entry.a1b2c3d4.js
├─ shared.91ab22cd.js
├─ settings.4d3c2b1a.js
├─ styles.7c3aed10.css
├─ logo.42f0c123.svg
└─ manifest.json
```

| 文件 | 用途 |
| --- | --- |
| entry chunk | 启动运行时和入口模块 |
| shared chunk | 多个异步页面共享的依赖 |
| async chunk | 动态 import 对应功能 |
| CSS | 从入口与依赖抽取的样式 |
| 资源 | 超过内联阈值的图片、字体等 |
| manifest | 记录逻辑 chunk 与实际文件名 |
| index.html | 注入入口 script 和 CSS link |

不要在业务代码中写死 hash 文件名。让 HTML、运行时和 manifest 负责关联。

## 公共路径 public_path

部署在域名根：

```toml
public_path = "/"
```

部署在 `https://example.com/console/`：

```toml
public_path = "/console/"
```

Electron 或 `file://` 本地页面：

```toml
public_path = "./"
```

它会影响异步 chunk 和资源 URL。常见错误是 HTML 能打开，但动态页面或图片请求到了域名根。

文档站使用独立配置：

```toml
[docs]
base_path = "/wake/"
```

也可以临时覆盖：

```bash
wake docs build . --base /wake/ --outdir docs-dist
```

命令行 `--base` 优先于配置。

## public 目录的差异

Wake Docs 会把 `public/` 递归复制到 `docs-dist`，并在与构建产物同名时失败，避免静默覆盖。

普通 `wake build` 当前主要把 `public/index.html` 作为 HTML 模板，不承诺复制其他 public 文件。应用图片和字体应从 TS/TSX/CSS 中 import，让 Wake 进入资源管线；或由部署步骤显式复制。

<Callout title="不要把源码放进输出目录" tone="warning">
`dist`、`docs-dist` 和 `.wake` 都是可再生成目录。构建会清理输出目录，手写文件可能丢失。业务源码、公共资源和部署脚本必须放在输出目录之外。
</Callout>

## 动态 import 与代码分割

```tsx title="src/router.tsx"
const SettingsPage = React.lazy(
  () => import("./pages/settings"),
);
```

Settings 会成为异步 chunk。只有运行到该页面时浏览器才加载它。共享依赖可能被提取到 shared chunk。

检查代码分割时不要只看文件数量，还要确认：

- 首屏没有加载所有异步 chunk；
- 切换页面时请求 URL 带正确 `public_path`；
- 部署服务器能返回带 hash 文件；
- 旧版本缓存不会与新 HTML 混用。

## Source Map 调试构建

```bash
wake build --sourcemap --outdir dist-debug
```

当前精确 Source Map 只支持非压缩路径，因此该选项会关闭压缩、mangle 和代码分割。它用于定位模块组合和源码位置，不应当作最终发布包。

建议把调试产物放到独立目录，避免误发布：

```text
dist/        正式发布
dist-debug/  临时排查
```

## 持久化缓存

```bash
wake build --cache
```

缓存写入 `.wake/cache.bin`，用于跨进程复用未变化模块的解析与代码生成结果。

缓存原则：

- 可以删除并重新生成；
- 不提交版本库；
- 配置、工具版本或输入变化会影响命中；
- 怀疑缓存问题时可删除 `.wake` 后做一次冷构建比较。

缓存用于加速，不应改变正确性。

## 常驻生产构建

```bash
wake build --watch
```

它首次构建后保持进程和构建引擎，文件变化时继续按生产口径重建。适合本地观察 production 行为，不等同于开发服务器，也不提供同样的 HMR 体验。

## 文档静态路由

Wake Docs 会生成：

```text
docs-dist/
├─ index.html
├─ 404.html
├─ getting-started/
│  └─ quick-start/
│     └─ index.html
└─ components/
   └─ button/
      └─ index.html
```

直接访问子路由时不必依赖服务端重写到根 index。仍建议部署完整目录，不要只上传根 HTML 和 assets。

## CI 示例

```yaml title=".github/workflows/docs.yml"
steps:
  - uses: actions/checkout@v4
  - uses: actions/setup-node@v4
    with:
      node-version: 22
      cache: npm
  - run: npm ci
  - run: wake docs build . --outdir docs-dist
  - name: Verify output
    run: test -f docs-dist/index.html
```

CI 还需要以团队确定的方式安装 Wake CLI。不要在脚本里依赖某位开发者电脑的绝对路径。

## 发布前检查清单

- [ ] 锁文件已提交，CI 使用冻结安装；
- [ ] production 命令从干净环境成功；
- [ ] `dist` 或 `docs-dist` 没有手写文件；
- [ ] 部署子路径与 `public_path`/`base_path` 一致；
- [ ] 入口 HTML 引用的 JS/CSS 都存在；
- [ ] 动态页面能够加载；
- [ ] 文档子路由直接访问不 404；
- [ ] `404.html` 已部署；
- [ ] draft 页面不在文档产物中；
- [ ] 没有 source map、密钥或本地绝对路径误入正式包；
- [ ] 准备了上一版本的回滚产物。

## 发布后检查

打开真实部署地址，不只检查首页：

1. 强制刷新一次；
2. 直接访问一个深层路由；
3. 打开一个 Demo；
4. 切换暗色主题；
5. 搜索一个 Props 名称；
6. 观察浏览器网络面板是否出现 404；
7. 从窄屏打开页面确认无横向溢出。

发布验证通过后再清理临时调试目录。

# 分包、性能与缓存

开发重建慢与生产页面加载慢需要分别测量。先定位耗时发生在哪里，再决定启用缓存还是拆分代码。

## 开发性能

保持同一个开发进程以复用增量结果。分别记录启动、修改到重建完成、重建到浏览器可用的时间；频繁重启和反复清缓存会使比较失去意义。

普通应用与 Docs 的编译范围不同。无自定义 UI、Preview 或 JSX runtime 的独立 Docs 开发站点可按访问构建页面和 Demo；首次访问仍可能等待编译。配置自定义 UI 或 Preview 时使用完整单图，生产、聚合和工作台也完整构建。这种选择保障共享 Context，不是“缓存没命中”。

## 生产缓存

带内容哈希的资源适合长期缓存，HTML 应短缓存或重新验证。不要将开发启动快与首屏网络少混为一谈；生产页面需要单独看请求瀑布、传输大小和交互就绪时间。

## 持久构建缓存

```bash
npx wake build --outdir dist --cache
```

缓存保存在 `.wake` 中，服务于可重建的派生结果。新进程仍读取真实源码内容，文件时间戳相同也不会跳过内容检查。缓存缺失或不兼容会重建；损坏和 I/O 问题可能给出非致命 WAKE_CACHE warning，不能把它当成源码编译错误。

## 代码分割

```ts title="src/report.ts"
export function reportText(): string { return "报告已加载"; }
```

```ts title="按需功能调用"
export async function loadReport(): Promise<string> {
  const { reportText } = await import("./report");
  return reportText();
}
```

让入口在真正需要报告时调用 loadReport。分块边界对应路由或重功能，不对每个小函数创建异步边界。打包器根据图决定具体输出，不以固定 chunk 数量作为业务契约。

## 测量方式

固定依赖锁文件、入口和选项，比较冷构建、无修改重复构建、单文件修改和生产资源总量。浏览器禁用缓存后查看初次加载，再触发报告，确认新增请求对应延后功能。检查缓存命中时也检查产物行为一致。

## 常见误区

缓存不是源码；不要部署 `.wake`。分包减少首屏负载的同时增加请求和初始化成本。命令输出的模块缓存统计也不代表所有缓存层的命中率，性能结论应有相同条件下的实际测量。
